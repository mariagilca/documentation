# Screenshot Automation Pipeline — Scoping Plan

**Status:** Proposed, not yet implemented
**Owner:** Docs infrastructure
**Decided upfront:** Playwright with saved-session auth; capture runs locally only (no CI secrets)
**Related:** audit-2026-05-12.md "Screenshot pipeline" (Later bucket), openlm-docs-audit-2026-06-09.docx §Carried-over strategic items
**Amended 2026-07-08:** resolution conventions superseded by [`image-quality.md`](./image-quality.md) — captures keep full 2× resolution (≥2,560 px, target 2,880); the former ≤1,600 px downscale is dropped because the image-zoom lightbox needs the native pixels.

## Problem

The site serves 2,015 raster images (mostly PNG), every one captured and cropped by hand. (A repo-wide reference scan on 2026-06-10 found 71 orphans — verified against `src/static/supported-software.json` and all dynamic consumers — which were deleted; the list is archived at `tooling/audits/orphaned-images-2026-06-10.txt`.) Each product release that changes the UI silently invalidates an unknown subset, and there is no way to tell which screenshots show the current product short of opening every page. Stale screenshots erode trust faster than missing ones: a reader who spots an outdated UI assumes the steps are outdated too.

Manual capture also produces inconsistent output. A 300-file sample shows the spread: 42% desktop-width (1200–1999 px), 29% medium, 21% small crops, 7% over 2000 px wide — different viewports, zoom levels, browser chrome, and themes, with no convention to anchor them.

### What changes and what doesn't

- `img/legacy/` (1,358 images, 65%) documents Version 25, a product in maintenance whose UI rarely changes. These are **out of scope** for automation — re-shooting them has no payoff.
- Cloud-product imagery (`img/engineering-lms/`, `services/*`, `img/reporting`, `img/saas-platforms`, ~480 UI screenshots) tracks an actively shipping product. This is the automation target.
- Icons, diagrams, and marketing art are out of scope; they are authored, not captured.

## Goals

1. Re-capture any cloud-UI screenshot from a one-line manifest entry, reproducibly: same viewport, theme, crop, and data every run.
2. Tie screenshots to product areas so a release note like "Homepage dashboard redesigned" answers "which images must be re-shot?" mechanically.
3. Make new screenshots cheap enough that writers stop hand-cropping.

## Non-goals

- Re-shooting the legacy library.
- CI-driven capture (revisit once the pipeline is trusted; keeping secrets out of Azure Pipelines is the deciding factor today).
- Localized JA screenshots. EN and JA docs share image assets today; keep that.
- Visual-regression testing of the product itself (that belongs to product QA).

## Architecture

A manifest-driven Playwright capture tool at `tooling/screenshots/`:

```
tooling/screenshots/
  manifest.yaml          # one entry per managed screenshot
  capture.mjs            # reads manifest, drives Playwright
  login.mjs              # one-time interactive login → .auth/state.json
  report.mjs             # staleness/diff report
  .auth/                 # storage states, gitignored
  README.md              # how to run; conventions summary
```

### Manifest schema

```yaml
defaults:
  viewport: { width: 1440, height: 900 }
  deviceScaleFactor: 2
  colorScheme: light
  maxWidthPx: 2880          # keep the full 2× capture — see image-quality.md; do not downscale

apps:
  cloud-us:   { baseUrl: "https://cloud-us.openlm.com",  storageState: ".auth/cloud-us.json" }
  cloud-eu:   { baseUrl: "https://cloud-eu.openlm.com",  storageState: ".auth/cloud-eu.json" }
  easyadmin:  { baseUrl: "https://easyadmin.openlm.com", storageState: ".auth/easyadmin.json" }

screenshots:
  - id: lac-rules-deployed
    output: static/services/lac/rules-deployed.png
    app: cloud-us
    route: /license-allocation/rules
    waitFor: "[data-testid=rules-table] tr"   # capture only after data renders
    clip: "section.rules-panel"               # CSS selector; omit for viewport shot
    mask: ["td.user-email", ".tenant-name"]   # PII redaction, Playwright mask
    area: lac                                  # product area, joins to releases
    usedBy:                                    # generated, do not edit
      - docs/cloud/slm/license-allocation.mdx
```

`area` is the key field: when a release ships for component X, `report.mjs --area X` lists every affected screenshot and its consuming docs. The `usedBy` list is generated by scanning `docs/` and `i18n/` for the output path, so the manifest can't drift from reality.

### Auth: saved session

One-time interactive login per app (`node login.mjs cloud-us` opens a headed browser; sign in, including MFA; the script saves Playwright `storageState` to `.auth/`). Capture runs reuse the state headlessly. States are gitignored and expire with the product's session policy; re-login is the documented fix for 401-pattern failures.

### Capture conventions (apply to manual shots too, starting now)

- Viewport 1440×900, `deviceScaleFactor: 2`, light theme, EN locale.
- PNG at full native 2× resolution (≥2,560 px wide for full-window shots — see [`image-quality.md`](./image-quality.md)), then lossless-optimized (oxipng — same pass the June 2026 audit applied; it cut the >800 KB set by 39%).
- No browser chrome, no OS shadows, no personal/customer data — capture from the demo tenant and use `mask` for anything dynamic.
- Filename = manifest `id`. New screenshots enter the manifest from day one; legacy filenames stay as-is until their page is next touched.

### Data prerequisite

Reproducible screenshots need reproducible data: a demo tenant with stable seeded entities (license servers, users, alerts). This is the one dependency outside the docs team — confirm with product whether the existing demo/staging tenant is stable enough, or whether a seed script is needed. **This is the main open question and the likeliest schedule risk.**

## Implementation phases

| Phase | Scope | Effort |
| --- | --- | --- |
| 1. Pilot | Scaffold tool + manifest for one section (`services/lac`, 10 images). Prove auth, masking, clip, optimization. | 2–3 days |
| 2. Cloud core | Onboard `services/*` and `img/reporting` (~120 images). Write `report.mjs` and the area→release mapping. | 1–2 weeks |
| 3. Integrations | `img/engineering-lms` + `img/saas-platforms` UI shots (~400). Mostly manifest data entry; batchable, internable. | 2–3 weeks, parallelizable |
| 4. Process | Release checklist step: run `report.mjs --area <released>` and re-capture before bumping `versions-*.json`. Document in CONTRIBUTING.md. | 1 day |

## Risks

- **Selector churn.** Product UI changes break `clip`/`waitFor` selectors. Mitigate: prefer `data-testid` attributes; ask product to treat them as a contract (they likely exist for product e2e tests already).
- **Flaky waits.** Dashboards render asynchronously. Mitigate: every entry has an explicit `waitFor`; no fixed sleeps.
- **Session expiry mid-run.** Detect the login redirect, fail fast with a "re-run login.mjs" message rather than capturing 50 login screens.
- **Demo-tenant drift.** Seeded data renamed or deleted changes every screenshot at once. Mitigate: seed script or a tenant nobody touches.
