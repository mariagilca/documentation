# OpenLM Documentation Style Guide

A practical reference for anyone authoring or editing pages in `docs/cloud/` and `docs/legacy/`. Where this guide is silent, defer to the [Splunk Style Guide](https://help.splunk.com/en/splunk-style-guide/welcome-to-the-splunk-style-guide). When the two conflict, this guide wins.

This guide pairs with the Vale rules in [`styles/OpenLM/`](styles/OpenLM/). Vale is the enforcement layer — this is the explanation layer.

---

## Tone and voice

Write for the busy engineer who's trying to get something done, not for the executive who's trying to be convinced.

- **Imperative voice for instructions.** "Install the Broker." not "You should install the Broker." not "The Broker can be installed."
- **Active voice for explanations.** "OpenLM Platform sends usage data to Reporting Service." not "Usage data is sent to Reporting Service by OpenLM Platform."
- **Second person.** Address the reader as *you*. Avoid *we*, *our*, *us*.
- **Present tense.** "The Broker collects license usage data." not "The Broker will collect license usage data."

## Words to avoid

The Vale rule in [`styles/OpenLM/DontUse.yml`](styles/OpenLM/DontUse.yml) catches these. Highlights:

| Don't write | Write instead |
| --- | --- |
| simply, just, easily | Cut the word. If something is easy, prove it by showing the steps. |
| please | Cut the word. "Run the installer." not "Please run the installer." |
| click | **select**. Covers mouse, keyboard, and touch. |
| note that, it is recommended that | Cut the phrase. State the recommendation directly. |
| in order to | to |
| due to the fact that | because |
| make sure that | confirm, verify, or ensure |
| a number of | several, many, or a specific count |
| above / below (for document locations) | previous, earlier / following, later |
| above / below (for software) | higher / lower |
| blacklist, whitelist | blocklist, allowlist |
| master / slave | primary / replica, or primary / secondary |
| sanity check | basic check, verification |
| aka, a.k.a. | also known as |
| realtime | real time (noun), real-time (adjective) |

Avoid hedges (*should*, *may*, *might*) when you mean a fact. *Should* is fine for recommendations: "You should restart the Broker after editing the config." Avoid it for behaviour: "The Broker restarts every 24 hours." not "The Broker should restart every 24 hours."

## Product terminology

- **OpenLM** — written without a leading article ("Install OpenLM Broker." not "Install the OpenLM Broker.") **except** when the product name acts as an adjective ("Configure the OpenLM Broker installer.").
- **OpenLM Platform** — the cloud product (formerly "OpenLM Cloud"). Refer to "the platform" (lowercase) on second mention if context is clear.
- **Annapurna** — deprecated internal codename for OpenLM Platform. Do **not** use it in published content; it dilutes the brand. Always write "OpenLM Platform" (or "the OpenLM Platform microservices" when referring to the architecture).
- **OpenLM Version 25 / v26** — the legacy product (releases v25 and v26). Write "OpenLM Version 25" (or "Version 25/v26 (legacy)" when both releases are in scope). Don't present legacy instructions as Platform.
- **Broker / Workstation Agent / DSA / SLM / SAM / LFM / VLM** — capitalised when referring to the product; lowercase when describing the role generically. **Broker** is shared and backwards compatible across Version 25 and Platform; **DSA** and **Workstation Agent** are built specifically for OpenLM Platform — don't describe them as cross-version.
- **EasyAdmin** — the legacy admin UI. Legacy only (legacy Cloud/SLMC and legacy on-premise); OpenLM Platform has no EasyAdmin. One word, camelCase.
- **EUS (End-User Services)** — legacy only. The server you install to provide the Personal Dashboard. In OpenLM Platform there is no separate EUS server.
- **SLMC (Software License Management Cloud)** — the legacy cloud offering. Legacy only. Spell out on first mention.
- **Personal Dashboard** — exists in both lines: served by the EUS server in legacy, built into OpenLM Platform. Don't tie it to a single version.
- **license / licence** — use *license* (US English).
- **license manager** — two words, lowercase. The product is *OpenLM License Parser*; the generic concept is *license manager*.

## Frontmatter

Every page under `docs/` needs frontmatter with at least:

```yaml
---
title: "Page title in sentence case"
description: "One sentence (under 155 characters) that would serve as a search snippet."
---
```

Additional fields when relevant:

- `sidebar_position: 3` — controls order within an autogenerated section.
- `slug: "my-page"` — overrides the URL segment derived from the filename.
- `keywords: [foo, bar]` — Algolia ranking hints.
- `tags: [changelog]` — sidebar tag filtering.

If you create a page, **fill in `description:`**. The Algolia snippet and the OpenGraph card both read from it. Auto-generated `description:` fields are acceptable as a starting point but should be replaced with intentional one-liners on the first edit.

## Headings

- **Sentence case** for all headings: H1, H2, H3. Capitalise the first word and any proper nouns. "Configure the Broker", not "Configure The Broker".
- **No body H1.** The frontmatter `title:` renders as the page H1. If you add `# My title` in the body, you create a duplicate H1, which is a WCAG violation. Start the body at `## H2`.
- **No trailing punctuation** in headings (no periods, no question marks unless the heading is genuinely a question — "What is OpenLM?").
- **Don't end a heading with a colon.**

The `OpenLM/HeadingCapitalization` Vale rule enforces sentence case; the `scripts/check-a11y-source.py` CI gate enforces the no-body-H1 rule.

## Admonitions

Use admonitions sparingly — overuse hides the signal.

The supported keywords (registered in `docusaurus.config.js`):

| Keyword | When to use |
| --- | --- |
| `:::note` | Side information the reader will want but doesn't need to act on. |
| `:::tip` | An optional improvement or shortcut. |
| `:::info` | Background context. Rarely needed in instructional docs. |
| `:::warning` | Something the reader can break if they don't pay attention. |
| `:::danger` | Data loss, security risk, or irreversible operation. |
| `:::discontinued` | Feature is removed or being removed. Pair with version info. |

Don't use `:::caution` — it's not registered and renders as the default style.

Optional title goes in square brackets: `:::warning[Restart required]`.

## Lists

- **Numbered lists** for instructions where order matters.
- **Bulleted lists** for items that don't have inherent order.
- **Don't mix.** If three items are steps and two are prerequisites, write a prerequisites paragraph or section, then a numbered procedure.
- Each list item should fit on a line at typical reading width. Long items become paragraphs.

Use a lead-in sentence for any list: "Confirm these prerequisites:" not a bare list under a heading.

## Code, commands, and UI elements

- **Inline code** for commands, filenames, paths, environment variables, configuration keys: `lmutil.exe`, `/etc/openlm/broker.conf`, `OPENLM_API_KEY`.
- **Bold** for UI element names: **License Managers**, **Save**, **Authorization** tab. Use bold once per element per section.
- **Code fences with a language hint** for multi-line code:

  ````
  ```bash
  sudo systemctl restart openlm-broker
  ```
  ````

- Show the prompt only when it matters for context. Don't include `$ ` unless you want the reader to ignore it.

## Procedures

The house pattern for a procedure page:

```
# (page title renders from frontmatter)

[One sentence that says what this page accomplishes and who it's for.]

## Before you begin

- Prerequisite 1.
- Prerequisite 2.

## [Verb-first section heading, e.g. "Configure the Broker"]

1. Step one.
2. Step two.
3. Step three.

## Verify

- Symptom or check that confirms success.

## Troubleshooting

[Common failure modes, each as an H3 question.]
```

Every step in a numbered list is one action — one sentence, one verb. If a step needs explanation, follow it with an indented paragraph or sub-list, not a comma splice.

## Links

- **Relative paths for internal links.** `[Broker Hub](./broker-hub)` from inside `data-collection/`, or absolute `[Broker Hub](/cloud/data-collection/broker-hub)` from anywhere.
- **Don't include the file extension.** `(/cloud/glossary)`, not `(/cloud/glossary.md)`.
- **Link text is the destination's title.** Don't write "click here" or "this article". Splunk style prefers descriptive anchor text.
- When you move or rename a page, **add a redirect** in `docusaurus.config.js` under `@docusaurus/plugin-client-redirects`. Don't fix inbound links by hand instead of redirecting — that breaks bookmarks.

## Images

Every image needs **non-empty alt text**. The CI script `scripts/check-a11y-source.py` enforces this and catches Japanese files where alt text was lost in translation.

- Describe what the image shows in plain language. "Broker UI showing the License Managers list with FlexNet detected."
- Don't write "image of" or "screenshot of" — assistive technology already announces it as an image.
- For decorative images (visual separators, logo lockups), use empty alt text intentionally only on raw `<img>` with `alt=""` and `aria-hidden="true"`. The MDX `![]()` syntax should always carry alt text.
- Pair every screenshot with a caption sentence in italics on the line below — it serves readers who can't see the image clearly and provides a second pass at the same content.

```markdown
![Broker UI with FlexNet detected automatically](/img/engineering-lms/flexera-flexnet-flexlm/image137.png)
*Automatic Broker detection of FlexNet*
```

## MDX components

Use the project's MDX components where they fit. See [`src/components/README.md`](src/components/README.md) for the inventory and how to import each one.

Highlights:

- `<Checklist>` and `<ChecklistItem>` for verification checkpoints.
- `<DeploymentCard>` / `<DeploymentCards>` on landing pages where the reader is choosing a path.
- `<DocLinkCard>` for "see also" sections that need more weight than a bullet list.
- `<DeprecationBanner>` at the top of legacy pages that have a cloud equivalent.

Don't roll your own JSX inside an MDX file when an existing component fits — it dilutes the design system and bloats the bundle.

## Localisation

- **English is the source of truth.** All edits happen in `docs/` first. JA copies live under `i18n/ja/` and update via `npm run write-translations -- --locale ja` plus manual translation.
- **Preserve frontmatter `id` and `slug` exactly** in JA files. Translating those breaks routing.
- **Preserve code fences, MDX imports, and admonition markers verbatim.** Only the prose translates.
- **Preserve alt text.** Don't ship a JA file with empty alt text where the EN file has alt text. CI catches this.

See [`project-guides/localization.md`](project-guides/localization.md) for the full flow.

## Numbers, dates, and units

- **Numbers under 10**: spelled out ("seven services") in prose; numerals in instructions and UI counts ("Select 3 records.").
- **Date format**: ISO 8601 — `2026-05-12`. In prose, "May 12, 2026" is fine; never write "5/12/26".
- **Units**: space between number and unit ("8 GB", "100 ms"). Use the standard abbreviation (`MB`, `GB`, `ms`, `s`).
- **Versions**: include the leading `v` ("v25.4", "v26.4.27"). Don't abbreviate to "25".

## Trademarks and third-party names

Capitalise as the vendor does: `FlexNet`, `FLEXlm`, `AutoCAD`, `MATLAB`, `Sentinel HASP`. When in doubt, look at the vendor's most recent product page.

Don't add `™` or `®` symbols except in legal text (the EULA, attribution lines on the homepage).

## Accessibility minimums

- Alt text on every image (covered above).
- No "click the red row" — describe the row by content, not colour.
- One H1 per page (covered above).
- Descriptive link text — no "click here".
- Headings nest properly — H2 → H3 → H4, no skipping levels.

The `scripts/check-a11y-source.py` script catches the first three at commit time; the axe-core CI run catches the rendered output.

## Common review comments

If you're seeing the same feedback repeatedly, look here first.

- **"Use 'select' not 'click'."** Always.
- **"Drop 'simply' / 'just' / 'please'."** Always.
- **"Sentence case the heading."** Especially in legacy pages where the original was title case.
- **"This page needs a `description:`."** Frontmatter, under 155 characters.
- **"Don't say 'we'."** Address the reader directly or use the product name.
- **"Move the H1 into the frontmatter."** `title:` field renders as H1; body should start at H2.
- **"Add a redirect."** When you rename, move, or split a page.

## Running the style check locally

```bash
npm run vale
```

Vale prints warnings, not errors — fix everything you can; flag the rest in your PR description. The CI gate will eventually enforce these (see the audit roadmap), so cleaning up at author time saves rework.
