# OpenLM Documentation — Audit and Roadmap Input

**Date:** 2026-05-12
**Scope:** `/Users/anamariagilca/projects/docs` (Docusaurus 3.10 site, deployed to `https://openlm.com/documentation/`)
**Lens:** Technical writer + information architect + React developer.

## How to read this

Findings are organised by theme. Each finding has:

- **What** — the observation, with concrete file paths and counts.
- **Why it matters** — impact on readers, SEO, contributors, or maintainers.
- **Effort** — `S` (under a day), `M` (a few days), `L` (one or more sprints).
- **Impact** — `low` / `medium` / `high`.

The closing section is a proposed roadmap (Now / Next / Later) drawn from the highest impact-to-effort items.

---

## Executive summary

The site is in good shape structurally. Docusaurus 3.10 + React 19, sensible swizzling, careful redirect plumbing, a custom Vale style based on the Splunk style guide, real CI with a11y gates, a working JA locale with near-1:1 file parity (550 EN / 549 JA), and a curated cloud sidebar that maps to a clear user journey. The cloud doc set has 100% frontmatter coverage for `title` and `description`.

The main risks and opportunities cluster in five areas:

1. **Two content sets that age at very different rates.** `docs/cloud` is well-tended; `docs/legacy` is largely stale — only 62% of files have a `title:` field, only 2% have a `description:`, and the original H1 lives in the body instead of the frontmatter. There is no published deprecation timeline or banner policy beyond the deprecation banner component itself.
2. **Soft enforcement everywhere.** `onBrokenLinks: 'warn'`, `onBrokenAnchors: 'ignore'`, axe-core scans only four URLs and is `exit 0`-gated, Vale never runs in CI, and `npm install --force` masks dependency conflicts. Each one is defensible alone; together they let regressions land silently.
3. **Style enforcement is configured but not wired up.** A robust `styles/OpenLM/` Vale package exists (~50 rules), but `npm run vale` is local-only and matches `*.md` (excluding the much larger `.mdx` surface area). The site has 874 occurrences of "click" (233 cloud, 641 legacy — Splunk style prefers "select"), 15 uses of "simply", and 270 files with a duplicate H1 (254 cloud + 16 legacy: frontmatter `title:` + body `# Heading`).
4. **Static and build payload are heavy.** `build/` is ~947 MB, `static/` is 249 MB across 2,485 images, with `static/img/legacy/` (180 MB) duplicated under `static/img/legacy/kb/`, several un-optimised PNGs above 800 KB, and a 1.85 MB GIF stored twice.
5. **Observability is missing.** No analytics, no feedback signal capture beyond an external Arcade link, no link checker beyond Docusaurus's warning-only mode, no broken-image detection. You can't see what's working without instrumentation.

Detailed findings follow.

## 1. Content and information architecture

### Strong foundations

- The cloud sidebar (`sidebars-cloud.js`) reads as a real user journey: Get started → Deployment → Data collection → Administration → Users → License tools → Reporting → Automations → Integrations → For end users → MCP → Reference → Changelog. The hand-wrapped `section()` helper preserves the `/cloud/category/<slug>` landing pages, which is the right call for SEO and shareable navigation.
- `docs/cloud` has 320 files, all with `title:` and `description:` in frontmatter. That's rare and worth defending.
- The `getting-started` flow has been split into discrete, well-frontmatter'd steps with `sidebar_position`, sentence-case headings, and consistent "Before you begin" blocks. The Splunk-style imperative voice is mostly intact.

### Issues and opportunities

**`docs/legacy` is a separate maintenance burden.**
228 files, but only 141 have a `title:` in frontmatter (62%), only 5 have a `description:` (2%), and most carry a body H1 that duplicates the page name. `docs/legacy/interfacing-articles/` alone holds 91 files. There is no written end-of-life policy in-repo — `support-lifecycle-and-platform-onboarding-policy.md` exists but isn't surfaced in the sidebar or as a header banner on legacy pages.
*Why it matters:* Missing `description:` hurts search snippets, Algolia ranking, and link previews. Legacy content keeps surfacing in Google but doesn't tell readers it's the older product. **Effort: M, Impact: high.**

**The "Understanding OpenLM" folder is empty in practice.**
`docs/cloud/understanding-openlm/` contains only `_category_.json`, `_faq/`, and `_feature-service-matrix.md` (all underscore-prefixed and excluded from the sidebar). The redirects in `docusaurus.config.js` move several pages out of it into `getting-started`. The folder either needs to be removed or repurposed; right now it's an empty shape that draft files live under.
*Why it matters:* IA hygiene; reduces confusion for contributors. **Effort: S, Impact: low.**

**Duplicate H1 in 270 files.**
Files have `title:` in frontmatter (which Docusaurus renders as the page H1) and a body `# Heading` (which becomes a second H1). This is flagged by `scripts/check-a11y-source.py` as a heading-structure violation. The script catches new violations; nothing back-fills the existing ones.
*Why it matters:* WCAG 1.3.1 (Info and Relationships) and 2.4.6 (Headings and Labels). Screen-reader users get an inconsistent heading hierarchy. **Effort: M (mechanical), Impact: high.**

**Top-level singletons in `docs/cloud/`.**
`compliance.md`, `dongle-monitoring.md`, `glossary.md`, `lfm.mdx`, `license-parser.md`, `sam.md`, `service-index.md`, `vlm.md` all sit at the cloud root rather than inside their sections. The sidebar bundles some into "License tools", but a flat root is hard to grep through and breaks the disk-mirrors-the-URL mental model.
*Why it matters:* Contributors waste time searching. **Effort: S, Impact: low.**

**Data-collection is a 162-file mega-section.**
The two subfolders (`engineering-lms/` with 101 files, `saas-platforms/` with 57) are the integration catalogue. They're well-organised inside, but the section landing page is generated-index — readers land on a wall of cards, not a guided path by license-manager family or by capability. The pre-existing audits (`tooling/audits/Engineering-License-Managers-Audit-2026-05-06.docx`, `tooling/audits/SaaS-Platforms-Audit-2026-05-06.docx`) suggest this is already on your radar.
*Why it matters:* Discoverability for a 160-page catalogue. **Effort: M, Impact: medium.**

**Stub pages still in the tree.**
`project-guides/intern-task-list.md` lists ~13 placeholder integration guides (`altair-managed.mdx`, `altiva.mdx`, `autodesk-token-flex.mdx`, `ibm-jazz.mdx`, etc.). Stubs that ship hurt readers more than missing pages do — they appear in search but answer no questions.
*Why it matters:* Trust. **Effort: M (write or remove), Impact: medium.**

**On-premise content has open TODOs in body.**
`docs/cloud/deployment-operations/on-premise/architecture-components.mdx` and four sibling files have `{/* TODO: Add link to Helm chart download location */}`-style comments still in place. These are MDX comments (won't render), but they signal incomplete pages that ship in production.
*Why it matters:* On-premise is a sales-relevant path. **Effort: S, Impact: medium.**

**Sidebar mixes flat docIds with autogenerated subtrees.**
`sidebars-cloud.js` uses `section()` helpers for most sections, but the "License tools" block hand-lists string doc IDs (`'lfm'`, `'vlm'`, `'sam'`, etc.). This works, but it means renaming a file silently breaks the sidebar without a build error (because `onBrokenLinks: 'warn'`).
*Why it matters:* Maintenance hazard. **Effort: S, Impact: low.**

**`audits/` is checked into the docs repo.**
The folder holds 18 Python scripts and 2 `.docx` audits totalling several hundred KB. There's also a stray `~$enlm-04.26-changelog-draft.docx` (Word lock file). These are useful artifacts but don't belong next to the docs source.
*Why it matters:* Repo hygiene; clones are heavier than necessary. **Effort: S, Impact: low.**

## 2. Writing quality and style

### Strong foundations

- Vale style package `styles/OpenLM/` contains ~50 rules adapted from the Splunk style guide, including `WordList.yml`, `ProductTerminology.yml`, `BiasFreeLanguage.yml`, `PassiveVoice.yml`, `HeadingCapitalization.yml`. The substitutions are well-thought-out (`abort` → `force quit, cancel, fail, close, stop, or end`).
- The cloud get-started pages model the house style well: imperative voice, sentence-case H2s, "Before you begin" front-loaded prerequisites, "Verification checklist" closers, no first-person.
- Zero uses of "please" in `docs/cloud`. Zero uses of "we recommend" / "our product". That's discipline.
- All 1,706 images across `docs/` have non-empty alt text.

### Issues and opportunities

**Vale isn't enforced in CI.**
`package.json` has `"vale": "vale --glob='*.md' docs"`. Two problems: the glob excludes `.mdx` (the majority of cloud integration pages), and the command is never invoked from `azure-pipelines.yml`. The Vale package is essentially decorative.
*Why it matters:* Style decisions don't stick without enforcement. **Effort: S, Impact: high.**

**874 occurrences of "click" across the site.**
233 in `docs/cloud`, 641 in `docs/legacy`. The Splunk style guide (which `OpenLM/WordList.yml` extends) prefers "select" because it covers mouse, keyboard, and touch. The Vale rule presumably catches this, but Vale doesn't run in CI and the rule's glob excludes MDX.
*Why it matters:* Accessibility (assumes mouse), terminology consistency. **Effort: M (find/replace with review), Impact: medium.**

**"Simply" appears 15 times.**
Splunk style forbids "simply" because what's simple to the writer rarely is to the reader. Concentrated in legacy (`openlm-applications-manager-configuration.md`, `pitfalls-in-license-utilization.md`, `openlm-virtual-license-manager-a-comprehensive-guide.md` etc.).
*Why it matters:* Tone. **Effort: S, Impact: low.**

**Admonition vocabulary drifts.**
`docusaurus.config.js` declares the admonition set as `['note', 'tip', 'info', 'warning', 'danger', 'discontinued']`. Actual usage: 292 `:::note`, 36 `:::info`, 27 `:::tip`, 19 `:::warning`, 2 `:::discontinued`, 2 `:::danger`, **1 `:::caution`** (not in the declared set — silently renders as default). The 1:1 caution should be `:::warning`.
*Why it matters:* Predictable visual language. **Effort: S, Impact: low.**

**Heading-style consistency between cloud and legacy.**
Cloud uses sentence case ("Verify your setup", "Before you begin"). Legacy mixes sentence and title case. If you eventually consolidate or selectively elevate legacy pages, you'll need a pass.
*Why it matters:* Style consistency across canonical search results. **Effort: M, Impact: low.**

**"Blacklist" still appears.**
`docs/cloud/dongle-monitoring.md:49` — `Add DeviceID of the dongle to **Blacklist**`. The OpenLM product UI likely says "Blacklist" too, so this is partly a product-localization issue, but the `BiasFreeLanguage.yml` Vale rule probably flags it.
*Why it matters:* Inclusive language. The doc can note "Blacklist (now labelled Blocklist in newer builds)" once the product changes. **Effort: S (doc-side note), Impact: low.**

**Frontmatter is great in cloud, weak in legacy.**
Restating from the IA section because it's also a writing-quality finding: cloud is 100% complete on `title`/`description`; legacy is 62%/2%. Mass-backfill descriptions in legacy (or autogenerate from the first paragraph as a quick win) and the search-result quality jumps.
*Why it matters:* SEO snippets and Algolia. **Effort: M, Impact: high.**

## 3. Build, tooling and CI

### Strong foundations

- The Docusaurus config is well-organised: docs as data, a `create_doc_plugin` factory, explicit `defaultSettings`, custom plugins for reading-time, last-updated, and an LLM-markdown export (smart move for AI-search visibility).
- The redirect block is genuinely careful — both a hand-written list and a `createRedirects(existingPath)` family generator that handles the `/cloud/services/*` → `/cloud/*` and `/interfacing-lms/` → `/connect-license-managers/` URL moves. The inline comment about hash-fragment limitations (`#arcgis-online`) is exactly the kind of institutional knowledge that belongs in code.
- Baseline security `<meta>` tags are set (X-Content-Type-Options, Referrer-Policy, Permissions-Policy) with a note that CSP/`frame-ancestors` need CDN-level configuration. Good awareness.
- `headTags` referrer-policy is `strict-origin-when-cross-origin`. Sensible default.
- Algolia AskAi keys are commented for swapping providers (Gemini vs Grok). Cute.
- CI runs source a11y checks, builds, runs axe, and rsyncs to production. The whole pipeline is in one YAML file you can audit in 90 seconds.

### Issues and opportunities

**Soft enforcement compounds.**
Each is justifiable in isolation. Together they leak regressions:

| Lever | Current setting | Effect |
| --- | --- | --- |
| `onBrokenLinks` | `'warn'` | Renamed pages and dead links ship silently. |
| `onBrokenAnchors` | `'ignore'` | Section anchors are never validated. |
| `onBrokenMarkdownLinks` | `'warn'` | Same, for Markdown-syntax links. |
| `axe-core` | scans 4 URLs, `exit 0` | New a11y violations don't fail CI. |
| `npm install --force` | always | Peer-dep conflicts hidden. |
| Vale | not in CI | Style violations don't block. |

*Why it matters:* The CLAUDE.md acknowledges #1 explicitly. The "right" answer is to flip them one at a time on a defined schedule, with a known-issues triage. **Effort: M (one switch per week), Impact: high.**

**Axe-core only scans four pages.**
`/index.html`, `/cloud/getting-started/what-is-openlm/`, `/privacy-policy/`, `/accessibility/`. With 550 doc pages, a single misbehaving custom component (e.g., `DeprecationBanner`, `Checklist`) would never be caught.
*Why it matters:* False sense of coverage. **Effort: M (parallelize axe across a sampled doc set, or use pa11y-ci with a sitemap), Impact: medium.**

**`npm install --force` in CI.**
`azure-pipelines.yml` line 70. With React 19 and Docusaurus 3.10 — combinations that may have peer-dep mismatches — `--force` papers over warnings that could become real failures later.
*Why it matters:* Hidden technical debt. **Effort: S (resolve the peer-dep conflicts once, then drop `--force`), Impact: medium.**

**Build artifact is 947 MB.**
That's the deployed payload size. Hot path pages (text + thumbnails) are small, but the long tail is heavy because of un-optimised PNGs and a 1.85 MB GIF. The `static/img/legacy/` and `static/img/legacy/kb/` trees are 180 MB combined, and several files appear in both (`gif.gif` 1.85 MB in each, `word-image-63206-*.png` files duplicated).
*Why it matters:* Deploy time, bandwidth, mobile load. **Effort: M (image-optim pass + de-dupe), Impact: medium.**

**Node version drift across files.**
CI: 22.x (`azure-pipelines.yml`). Dockerfile: `node:lts` (currently 22 but moves). `package.json`: `engines.node >= 18.0`. Pin a single version everywhere; align with `.nvmrc` so contributors' local dev matches production.
*Why it matters:* "Works on my machine" risk. **Effort: S, Impact: low.**

**No `.github/` directory.**
No CODEOWNERS, no PR template, no issue templates, no Dependabot config, no pre-commit. The repo is on Azure Pipelines for CI but presumably on GitHub for source — even a thin PR template and CODEOWNERS file improves review consistency.
*Why it matters:* Contributor experience. **Effort: S, Impact: medium.**

**No link checker.**
With `onBrokenLinks: 'warn'`, you need an external link checker to catch dead external URLs (and to act as a safety net for internal ones until you tighten the policy). `lychee`, `linkinator`, or `lint-staged` + `remark-lint-no-dead-urls` are options.
*Why it matters:* Trust. **Effort: S, Impact: medium.**

**Stale Word lock file checked into the repo root.**
`~$enlm-04.26-changelog-draft.docx` (162 bytes). The `.gitignore` does include `~$*` and `*.tmp`, so this snuck in before the rule was added. Worth cleaning up.
*Why it matters:* Hygiene. **Effort: S, Impact: low.**

**Audit scripts live in `docs/audits/`.** *(Resolved 2026-05-12: moved to `tooling/audits/` with a README; `.docx` outputs continue to be tracked at their new location, future ones are gitignored.)*
18 Python files (`build_engineering_lms_audit.py`, `track4b_*.py` etc.) and two `.docx` audits. If they're tooling, they belong in a sibling repo or a `tooling/` directory; if they're outputs, they belong in cloud storage with a link in `project-guides/`.
*Why it matters:* Repo focus. **Effort: S, Impact: low.**

## 4. UX, theme and performance

### Strong foundations

- 22 custom React components in `src/components/`, including domain-specific ones like `DeploymentCard`, `Checklist`, `DocLinkCard`, `InstallationInstructions`. This is the right move — MDX wins when the building blocks fit the content.
- Swizzled theme is targeted, not sprawling: 13 components, focused on Footer, Navbar, Layout, DocItem, SearchBar, DocCategoryGeneratedIndexPage. The DocItem swizzle includes a `CopyPageButton` integration, which is exactly the kind of LLM-era affordance that pays off.
- The hero fluid sim is gated on `prefers-reduced-motion`, WebGL1 + half-float availability, and viewport size (smaller grids on phones, DPR capped at 1.0 on small screens). The dynamic `import('./fluid')` keeps the 1,182-line sim out of the SSR bundle. The fallback is the CSS gradient. Genuinely well done.
- Algolia DocSearch is configured with `contextualSearch: true`, `askAi: 'gOVYMNBglLuQ'` (Grok), `insights: true`, search-result path rewriting, and a custom `/search` page. Modern setup.
- The `llm-markdown` plugin emits LLM-friendly `.md` exports including release-notes JSON rendering. Forward-looking — this is how docs sites stay useful when half the traffic is LLM agents.
- `robots.txt` explicitly allows `OAI-SearchBot`, `GPTBot`, `Google-Extended`, `ClaudeBot`. Considered, not accidental.

### Issues and opportunities

**Algolia Insights ships before consent.**
`insights: true` in `docusaurus.config.js`. The `project-guides/consent-banner-integration-plan.md` document is comprehensive (Klaro vs. custom, GDPR/ePrivacy framing) and marked "Approved, not yet implemented". This is a privacy-compliance gap with a written plan and no ship date.
*Why it matters:* Legal exposure under GDPR Article 6 / ePrivacy Article 5(3); equivalent issues for Arcade demo embeds. **Effort: L (Klaro path looks right), Impact: high.**

**No analytics.**
No Plausible, no GA, no PostHog. You can't measure which pages convert, which integrations get viewed, which redirects fire. Adding analytics has to come paired with the consent banner above.
*Why it matters:* You're optimising blind. **Effort: M (with consent banner), Impact: high.**

**No in-doc feedback signal.**
The footer links to an Arcade-hosted feedback form. That's external, low-friction for the writer but high-friction for the reader, and you don't see per-page signal. A "Was this helpful?" widget on each page (with optional comment, no PII) gives you a leading indicator that's much cheaper than user research.
*Why it matters:* You can't fix what you can't see. **Effort: M, Impact: high.**

**No structured data / JSON-LD.**
No `<script type="application/ld+json">` for `TechArticle`, `Breadcrumb`, `SoftwareApplication`. Docusaurus generates basic OG/Twitter tags via the theme; explicit JSON-LD improves rich results.
*Why it matters:* Search snippets and AI-search citations. **Effort: M, Impact: medium.**

**Announcement bar is date-gated by hardcoded date.**
`ANNOUNCEMENT_RELEASE_DATE = new Date('2026-04-28')` and a 7-day visibility window. Every release means a config edit. Move to a `static/announcement.json` that the build reads, or a single environment variable, and the marketing team can update without a code change.
*Why it matters:* Velocity for announcements. **Effort: S, Impact: low.**

**Hero `aria-hidden="true"` on the fluid canvas is correct, but the surrounding hero needs a check.**
The canvas itself is decorative. The hero region around it (in `HomepageHeader`) needs a meaningful `<h1>` and a skip-to-content link. Worth a quick screen-reader pass on the landing page specifically.
*Why it matters:* Landing page is the most-linked URL. **Effort: S, Impact: medium.**

**Image weight.**
On top of the build-size finding: a 2.93 MB `high-level-architecture.jpg`, several 800 KB+ PNGs, a 1.85 MB GIF stored twice. None of these were authored at web sizes. A one-time `oxipng`/`mozjpeg`/`gifsicle` pass plus a check that high-res screenshots get 1.5x DPR variants would help LCP, especially on mobile.
*Why it matters:* Mobile readers and Lighthouse scores. **Effort: M, Impact: medium.**

**Dark mode QA gap.**
The CLAUDE.md says "open the page in the browser and check both light and dark color modes" but there's no automated dark-mode capture. With 22 custom components and 13 theme overrides, a Playwright snapshot pass that toggles `[data-theme="dark"]` would catch regressions before customers do.
*Why it matters:* Half your audience uses one mode you're not testing. **Effort: M, Impact: medium.**

## 5. Gap analysis — what's missing

These are absences rather than defects. They show up because of where the project is heading, not where it is.

**Style guide isn't published.**
The `styles/OpenLM/` Vale rules encode the house style, but there's no `STYLE_GUIDE.md` (or equivalent) that contributors can read. A short guide that points at Splunk's style guide, lists the OpenLM-specific exceptions (product names, capitalization rules), and explains "why" makes onboarding ten minutes instead of a week.
**Effort: S, Impact: high.**

**Versioning policy isn't written.**
Docusaurus's docs-versioning is configured (`lastVersion: 'current'`, version label "OpenLM Platform"), but there's no decision recorded about when you snap a version, what triggers it (semver? quarterly?), and how legacy ends. `project-guides/architecture.md` covers structure but not lifecycle.
**Effort: S (write the policy), Impact: medium.**

**Legacy sunset plan isn't surfaced.**
`docs/legacy/support-lifecycle-and-platform-onboarding-policy.md` exists, but it's not pinned at the top of every legacy page (the `DeprecationBanner` component is custom and would be a good vehicle), and it's not reflected in `robots.txt` or `noindex` for pages clearly slated for removal.
**Effort: S, Impact: high.**

**No release-aligned docs review.**
No CI step ties product releases to doc updates. Workstation Agent v26.4.27 and Broker v26.4.30 ship and the announcement bar lights up, but there's no mechanism that requires the relevant doc pages have a `last_updated` newer than the release date.
**Effort: M, Impact: medium.**

**No contribution metrics.**
The `last-updated` plugin records timestamps. Surfacing a "doc health" page (last touched > 12 months ago, files without descriptions, broken-link warnings, oldest images) lets you triage the long tail without doing a full audit each time.
**Effort: M, Impact: medium.**

**No screenshot pipeline.**
2,485 images in `static/`. Each is a manual update. A scripted Playwright/Puppeteer screenshot pass for product UI screens — even just a documented convention — saves hours per release and prevents stale visuals that erode trust.
**Effort: L (worth scoping), Impact: high.**

**JA translation is impressive but unverified.**
549 JA files for 550 EN files: near-parity. But there's no test that catches an EN-only update silently leaving a JA file behind. The `check-a11y-source.py` script already does alt-text parity; expand to "title parity" and "outline parity" (same H2 set, same number of code blocks, same number of `:::warning` admonitions).
**Effort: M, Impact: medium.**

**Search isn't tuned with synonyms.**
Algolia is set up, but I don't see synonyms configured (e.g. "FLEXlm" ↔ "FlexNet" ↔ "Flexera", "Broker" ↔ "OpenLM Broker" ↔ "broker hub"). The product has a lot of multi-name terminology; Algolia's synonyms feature is the highest-leverage search improvement you can make in an afternoon.
**Effort: S, Impact: high.**

**No "how to contribute" path for non-employees.**
`CONTRIBUTING.md` is 157 lines and developer-facing. There's no "I found a typo — what do I do?" entry point on the site itself. A footer "Edit this page on GitHub" link (Docusaurus has built-in `editUrl` config) plus a 5-line `SECURITY.md` covers a lot of ground.
**Effort: S, Impact: low.**

**MDX-component documentation.**
22 custom components, no inventory. Writers can't reach for `<DeploymentCard>` if they don't know it exists. A `src/components/README.md` that lists each component, what it's for, what props it takes, and where it's used pays off forever.
**Effort: S, Impact: medium.**

**Accessibility statement isn't connected to data.**
The axe-core CI step references "the known-barrier list from the accessibility statement" — implying there's a published statement at `/accessibility/`. Worth ensuring it's current and links to a real remediation tracker, not a static page.
**Effort: S, Impact: medium.**

## 6. Proposed roadmap

A way to sequence the above. Each bucket is one quarter at typical doc-team pace.

### Now (this quarter — quick wins and risk reduction)

1. **Wire Vale into CI and expand its glob to `*.md,*.mdx`.** (S, high) The style package already exists; this turns it on.
2. **Backfill `description:` in `docs/legacy`.** (M, high) Even auto-generated from the first paragraph is a 10x improvement over nothing.
3. **De-duplicate `static/img/legacy/` and `static/img/legacy/kb/`; run an image-optim pass on >500 KB assets.** (M, medium) Should shave 100+ MB off the deploy.
4. **Publish `STYLE_GUIDE.md` and `src/components/README.md`.** (S, high) Pure documentation; no code changes.
5. **Add a "Was this helpful?" widget tied to the consent banner.** (M, high — bundle with the banner work) Most leverage per dollar in the audit.
6. **Configure Algolia synonyms for license-manager families.** (S, high)
7. **Ship the consent banner.** (L, high) Plan exists, just needs the work. Unlocks analytics.
8. **Remove dead files: stub legacy pages with no real content, `~$enlm-04.26-changelog-draft.docx`, empty `understanding-openlm/` folder.** (S, low)

### Next (one to two quarters out — durable improvements)

9. **Migrate to `onBrokenLinks: 'throw'`, `onBrokenAnchors: 'warn'`, drop `--force` from `npm install`.** (M, high — one switch per fortnight with a triage queue)
10. **Back-fill the 270 duplicate-H1 violations.** (M, high) Largely mechanical script + spot-check.
11. **Expand axe-core to a sampled set of doc pages, then enforce.** (M, medium) `pa11y-ci` against the sitemap with a budget.
12. **JA outline-parity check.** (M, medium) Extend `check-a11y-source.py`.
13. **Auto-redirect plus deprecation banner on every `docs/legacy/*` page that has a cloud equivalent.** (M, high)
14. **Doc-health dashboard page (last touched, descriptions missing, etc.).** (M, medium)
15. **JSON-LD `TechArticle` + `BreadcrumbList` injection via theme.** (M, medium)
16. **Move `audits/` and Python scripts out of the docs repo.** ✅ *Done 2026-05-12: relocated to `tooling/audits/` with a README and migration-script inventory.*

### Later (next year — strategic)

17. **Screenshot automation pipeline.** (L, high) Pays for itself within two product releases.
18. **Re-think the data-collection catalogue: facet-search by capability and family.** (L, medium) The 160-file flat catalogue is at the size where readers need filters, not just sidebars.
19. **Versioning policy + first cut.** (M, medium) Decide when to snap v26 and how.
20. **Move announcement-bar config to data-driven file.** (S, low)
21. **Add a `release-doc gate` GitHub Action that fails a release PR when relevant docs haven't been touched.** (M, medium)

### Sequencing logic

The "Now" bucket is dominated by hygiene wins that don't require new infrastructure — they leverage what already exists (Vale package, last-updated plugin, redirect plumbing). The "Next" bucket is where you tighten the soft-enforcement levers, which only makes sense after the existing violations are cleaned up.
