Frequently asked questions (FAQ)

How to use this FAQ

Click on a question to expand and read the answer. Each topic provides clarity about OpenLM Annapurna’s deployment and infrastructure expectations.

Deployment process​

How are the Annapurna microservices deployed in Kubernetes? Is that why the host machine needs internet access?

They are deployed using Helm charts. We use an "umbrella chart" (monohelm), which allows you to deploy multiple services with a single chart. You configure which services to deploy using the values.yaml file. Services can be enabled or disabled, but you must manually control the order — Helm does not handle service dependencies automatically.

Internet access is required to pull Docker images from AWS ECR and retrieve Helm charts from a public Helm repository (this is a work in progress).

Service communication​

How do services discover and communicate with each other? Is Kubernetes DNS used or a service mesh? How does it connect to external services like MongoDB or Kafka?

Services communicate over HTTP using Kubernetes DNS. For asynchronous communication, services use Kafka as a message broker.

External infrastructure services like MongoDB, Redis, Kafka, and SQL Server are configured using connection strings that include host, port, credentials, and options. These external hosts must be accessible from Kubernetes nodes.

Database schema management​

Are database schemas version-controlled and automatically updated?

Yes. Migrations for both SQL and MongoDB are version-controlled and applied automatically. No manual operational support is needed during upgrades.

DNS and ingress routing​

How should the domain used by the UI and agents be resolved? Is a specific FQDN required?

Yes. You must configure a fully qualified domain name (FQDN) and import a TLS certificate into Kubernetes as a TLS secret. We use the NGINX ingress controller, which must be installed in the cluster. Agents will connect to the system using this FQDN.

Note: The TLS certificate must support at least 3 chain handshakes: original issuer → intermediate issuer → final root issuer.

Storage requirements​

Which services require persistent volumes? What are the size and performance expectations?

If you're deploying infrastructure services within Kubernetes, persistent volumes will be needed. General recommendations:

  • MongoDB: Medium IOPS, 30GB+ storage, 20+ IOPS
  • Redis: Low IOPS, 5GB+ storage, 10+ IOPS
  • Kafka: High IOPS, 50GB+ storage, 30+ IOPS

SQL Server is usually deployed outside Kubernetes, so storage is configured separately. For our internal use, we recommend 5GB+ with 20+ IOPS.

Among OpenLM services, only the reporting (Spark) service uses a volume — 2GB in ReadWriteMany mode for pod synchronization.

Container image sources​

Are containers pulled from public or private registries? Can you provide a list of required endpoints for firewall configuration?

All containers are pulled from public registries. Our main image registry is AWS ECR:
public.ecr.aws/r3q3q2f4/

Additional image sources include:

  • docker.tyk.io/tyk-gateway/
  • docker.io/library/

We also use images from open-source project registries. If required, you can mirror these to an internal registry to avoid external dependencies.

Database compatibility​

Is Microsoft SQL Server required, or can we use alternatives like PostgreSQL?
  • For operational data, you can use SQL Server, MySQL, or MariaDB.
  • For reporting data, you can use SQL Server or PostgreSQL.

SQL Server is the only DBMS compatible with both operational and reporting needs, which is why we recommend it. However, it's possible to use MariaDB for operational data and PostgreSQL for reporting if you prefer open-source solutions.

MongoDB is mandatory and does not have an on-prem alternative.

Internet access​

Is generic internet access always required? Can we restrict it with an allowlist?

Internet access is only required for image pulls and optional Kubernetes installation steps. Runtime does not depend on internet access.

If you need to restrict internet access, you can mirror required images to an internal registry. Installing Kubernetes offline is possible, but significantly more complex.

Having an allowlist of external endpoints is useful during initial setup and simplifies troubleshooting.
