## デプロイメントプロセス

<details>
<summary>OpenLM Platform のマイクロサービスは Kubernetes 上にどのようにデプロイされますか？ ホストマシンにインターネットアクセスが必要なのはそのためですか？</summary>

Helm チャートを使ってデプロイされます。OpenLM では「アンブレラチャート」（monohelm）を使用しており、1 つのチャートで複数のサービスをデプロイできます。デプロイするサービスは `values.yaml` で構成します。サービスは有効化／無効化できますが、サービスの依存関係を Helm が自動的には扱わないため、デプロイ順序は手動で制御する必要があります。

インターネットアクセスは、AWS ECR からの Docker イメージのプルと、パブリック Helm リポジトリからの Helm チャート取得のために必要です（こちらは現在対応中です）。
</details>

## サービス間通信

<details>
<summary>サービス同士はどのように検出し合い、通信しますか？ Kubernetes DNS が使用されますか、それともサービスメッシュですか？ MongoDB や Kafka などの外部サービスとはどのように接続しますか？</summary>

サービスは Kubernetes DNS を介して HTTP で通信します。非同期通信には、メッセージブローカーとして Kafka を使用します。

MongoDB、Redis、Kafka、SQL Server などの外部インフラサービスは、ホスト、ポート、認証情報、オプションを含む接続文字列を使って構成します。これらの外部ホストは Kubernetes ノードからアクセス可能である必要があります。
</details>

## データベーススキーマ管理

<details>
<summary>データベーススキーマはバージョン管理され、自動的に更新されますか？</summary>

はい。SQL と MongoDB の両方のマイグレーションはバージョン管理されており、自動的に適用されます。アップグレード時に手動の運用作業は不要です。
</details>

## DNS と Ingress ルーティング

<details>
<summary>UI とエージェントが使用するドメインはどのように解決すべきですか？ 特定の FQDN が必要ですか？</summary>

はい。完全修飾ドメイン名（FQDN）を構成し、TLS 証明書を Kubernetes に TLS シークレットとしてインポートする必要があります。OpenLM では NGINX Ingress コントローラーを使用しており、クラスタにインストールされている必要があります。エージェントはこの FQDN を使ってシステムに接続します。

> 注：TLS 証明書は、少なくとも 3 段階のチェーン検証（オリジナル発行者 → 中間発行者 → 最終ルート発行者）に対応している必要があります。
</details>

## ストレージ要件

<details>
<summary>どのサービスに永続ボリュームが必要ですか？ サイズとパフォーマンスの想定は？</summary>

Kubernetes 内にインフラサービスをデプロイする場合は、永続ボリュームが必要です。一般的な推奨値は次のとおりです：

- **MongoDB**：中程度の IOPS、30GB 以上のストレージ、20 IOPS 以上
- **Redis**：低 IOPS、5GB 以上のストレージ、10 IOPS 以上
- **Kafka**：高 IOPS、50GB 以上のストレージ、30 IOPS 以上

SQL Server は通常 Kubernetes の外でデプロイされるため、ストレージは別途構成します。内部利用の場合は、5GB 以上、20 IOPS 以上を割り当ててください。

OpenLM サービスのうち、ボリュームを使用するのは reporting（Spark）サービスのみで、Pod 間の同期のために `ReadWriteMany` モードで 2GB を使用します。
</details>

## コンテナイメージの取得元

<details>
<summary>コンテナはパブリックとプライベートのどちらのレジストリから取得されますか？ ファイアウォール構成のために必要なエンドポイントの一覧を提供できますか？</summary>

すべてのコンテナはパブリックレジストリから取得されます。メインのイメージレジストリは AWS ECR です：  
`public.ecr.aws/r3q3q2f4/`

その他のイメージ取得元は次のとおりです：

- `docker.tyk.io/tyk-gateway/`
- `docker.io/library/`

オープンソースプロジェクトのレジストリからのイメージも使用しています。必要に応じて、外部依存を避けるためにこれらを内部レジストリにミラーリングできます。
</details>

## データベース互換性

<details>
<summary>Microsoft SQL Server は必須ですか、それとも PostgreSQL などの代替を使用できますか？</summary>

- **運用データ**：SQL Server、MySQL、または MariaDB を使用できます。
- **レポーティングデータ**：SQL Server または PostgreSQL を使用できます。

運用とレポーティングの両方に対応する DBMS は SQL Server のみであるため、可能な限り SQL Server を使用することをお勧めします。ただし、オープンソースを優先する場合は、運用データに MariaDB、レポーティングに PostgreSQL を使うこともできます。

> MongoDB は必須であり、オンプレミスの代替手段はありません。
</details>

## インターネットアクセス

<details>
<summary>常に汎用的なインターネットアクセスが必要ですか？ 許可リスト（allowlist）で制限できますか？</summary>

インターネットアクセスが必要なのは、イメージのプルと Kubernetes インストール時の任意の手順のみです。ランタイムはインターネットアクセスに依存しません。

インターネットアクセスを制限する必要がある場合は、必要なイメージを内部レジストリにミラーリングできます。Kubernetes をオフラインでインストールすることも可能ですが、難易度はかなり高くなります。

> 外部エンドポイントの許可リストを用意しておくと、初期セットアップやトラブルシューティングが容易になります。
</details>
