OpenLM はマイクロサービス全体で GraphQL API を提供しており、ライセンス分析データへの構造化されたプログラム的アクセスを可能にします。各サービスは `/graphql` エンドポイントと、対話型の GraphQL IDE（`/graphql/ui`）を提供します。

GraphQL API でできること：

- ライセンス使用状況、拒否、コンプライアンス、調達データのクエリ
- ユーザー、グループ、ワークステーション情報の取得
- License Access Control ルールやライセンスファイルデプロイの管理
- レポーティングの自動化と、外部ツールとの連携

## 認証

すべての OpenLM サービスは、OpenLM Identity Server を介した OAuth 2.0 + Proof Key for Code Exchange (PKCE) を使用します。`AuthSetup.AuthSettings.EnableSecurity` が `true` の場合、すべてのリクエストの `Authorization` ヘッダーに有効な JSON Web Token (JWT) Bearer トークンを含める必要があります。

```
Authorization: Bearer <your-access-token>
```

セキュリティが無効（開発モードのみ）の場合は、エンドポイントは匿名アクセスを許可します。

### 認可ポリシー

各サービスは、次のポリシーを通じてロールベースアクセス制御を適用します：

| ポリシー | アクセスレベル |
|--------|-------------|
| AdminAccessPolicy | 作成・読み取り・更新・削除のフルアクセス |
| ViewerAccessPolicy | 読み取り専用アクセス |
| SysAdminPolicy | システム管理者向け操作（クラウド） |
| CloudAccessPolicy | クラウドレベルの操作 |

## リクエストの流れ

クエリを送信すると、API は次の手順でリクエストを処理します：

1. **クエリの送信** — アプリケーションは、必要なフィールド、フィルター、ソート、ページネーションパラメーターを含めて、GraphQL リクエストをサービスエンドポイントに送信します。
2. **API による認証とテナント解決** — API は呼び出し元の ID を検証し、接続すべき顧客データベースを判定します。
3. **クエリの実行** — API は GraphQL リクエストを、構成済みバックエンドに最適化されたデータベースクエリに変換します。
4. **結果の返却** — レスポンスは、ページネーションメタデータとともに構造化された JSON として返されます。

```
アプリケーション -> GraphQL クエリ -> OpenLM サービス -> データベース -> 構造化 JSON レスポンス
```

## 一般的なクエリパターン

### ページネーション

OpenLM サービスは 2 種類のページネーションスタイルをサポートします：

- **オフセットベース**：`skip` と `take` 引数を使用します。シンプルなページ移動向けです。
- **カーソルベース**：Relay 仕様に従い、`first`、`after`、`before`、`last` 引数を使用します。一貫したページネーションが重要な大規模データセット向けです。

ページネーションされるすべてのクエリは `totalCount` をサポートします。

**オフセットベースの例：**

```graphql
query {
  users(tenantId: "my-tenant", skip: 0, take: 25) {
    items {
      username
      email
    }
    totalCount
  }
}
```

**カーソルベースの例：**

```graphql
query {
  denials(first: 10, after: "cursor-value") {
    nodes {
      denialId
      vendor
    }
    totalCount
    pageInfo {
      hasNextPage
      endCursor
    }
  }
}
```

### フィルタリング

`where` 引数とフィールド固有の演算子を使って結果を絞り込みます。一般的な演算子には `eq`、`neq`、`contains`、`in`、`gt`、`lt` などがあります。

```graphql
query {
  users(tenantId: "my-tenant", where: { isEnabled: { eq: true } }) {
    items {
      username
      email
    }
  }
}
```

一部のサービスは、大文字小文字を区別しない部分一致検索のためのカスタム `icontains` 演算子もサポートします。

### ソート

`order` 引数にフィールド名と `ASC` または `DESC` を指定します。

```graphql
query {
  denials(first: 20, order: [{ denialId: DESC }]) {
    nodes {
      denialId
      vendor
    }
  }
}
```

## マルチテナントデータ分離

API は厳格なマルチテナントアーキテクチャ上で動作します。各顧客のデータは完全に分離されています：

- 各顧客のデータは、専用の独立したデータベースに格納されます。
- API は認証セッションを通じて、すべてのリクエストで顧客 ID を検証します。
- API は認証されたテナントに基づき、対応する正しいデータベースに動的に接続するため、テナント間のデータアクセスは発生しません。

## パフォーマンスとキャッシング

API には次のパフォーマンス最適化が含まれています：

- **組み込みキャッシュ** — 構成可能な TTL（time-to-live）を使い、繰り返されるクエリにキャッシュを返すことで、頻繁にアクセスされるデータのレスポンス時間を短縮します。
- **ページネーション** — すべてのリストクエリは既定でページネーションされ、効率的なデータ転送と過大なレスポンスの防止を実現します。
- **接続プーリング** — 接続プールがデータベース接続を管理し、リソース利用とクエリスループットを最適化します。
- **キャッシュ無効化** — 最新データが必要なときは、オンデマンドでキャッシュをクリアできます。

最適なパフォーマンスのためには、フィルターでクエリを絞り込み、必要なページサイズのみをリクエストしてください。小さく焦点を絞ったクエリのほうが応答が速く、消費するリソースも少なくなります。

## サポートされているデータベースバックエンド

Reporting API は複数のデータベースバックエンドに対応しています：

| データベース | ユースケース |
|----------|----------|
| SQL Server | オンプレミスおよびハイブリッドデプロイメント |
| PostgreSQL | オンプレミスおよびクラウドデプロイメント |
| AWS Athena | S3 ベースのデータレイクを利用するクラウドデプロイメント |

API は構成済みのデータベースバックエンドに合わせてクエリ生成を自動的に調整するため、基盤インフラに関係なく一貫した結果が得られます。バックエンドを切り替える際にコードを変更する必要はありません。

## セキュリティのハイライト

| 機能 | 説明 |
|---------|-------------|
| 認証 | OpenLM Identity Server を介した OAuth 2.0 + PKCE |

| データ分離 | 顧客ごとに専用データベースを用意し、リクエストごとに動的に解決 |
| 通信のセキュリティ | HTTPS により、すべての通信を暗号化 |
| アクセス制御 | API リクエストごとに JWT ベースのトークン検証 |
| 読み取り専用アクセス | Reporting API はレポーティングデータへの読み取り専用アクセスを提供します。ソースデータの変更はできません。 |
